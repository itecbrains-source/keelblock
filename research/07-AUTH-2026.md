# Auth on Supabase and Next.js 16 — what is actually true in September 2026

_Researched 2026-09-08, before SPEC-004 was written. **Five things I would have written from
recollection are wrong**, and one of them is a cross-user session leak. That is the argument for the
ordering: a memo written after the spec would have been written to agree with it._

## What recollection would have got wrong

### 1 · `middleware.ts` is deprecated; the file is `proxy.ts`

Next.js **16.0.0 renamed the `middleware` convention to `proxy`** and the docs mark middleware
deprecated. Proxy also now defaults to the Node.js runtime, and setting `runtime` in a proxy file
throws. There is a codemod (`npx @next/codemod@canary middleware-to-proxy .`).

This repository ships `src/middleware.ts` on Next `16.3.4`. It works — the convention is deprecated,
not removed — but every auth guide worth copying is now written against `proxy.ts`, and Supabase's
own Next.js guide already says "Proxy" throughout.

The renaming rationale matters more than the rename. From the Next.js documentation:

> _"We recommend users avoid relying on Middleware unless no other options exist."_

and, on why the name changed: _"The term 'proxy' implies a network boundary in front of the app…
It can run outside of your application's main runtime."_ **A network boundary in front of the app is
not an authorization boundary**, which is the whole design constraint for SPEC-004.

### 2 · The verification call is `getClaims()`, not `getUser()`

The advice I carried was "on the server, always `getUser()`, never `getSession()`". Half right, and
the wrong half is the recommendation. Current Supabase guidance:

> _"Never trust `supabase.auth.getSession()` inside server code such as Proxy. It isn't guaranteed to
> revalidate the Auth token."_

> _"It's safe to trust `getClaims()` because it validates the JWT signature against the project's
> published public keys every time."_

The three-way split is now explicit: `getClaims` **to verify identity — the authorization call**,
`getUser` when a fresh user record from the Auth server is genuinely needed, `getSession` only for
the tokens, never for its user object. All three exist in the pinned `@supabase/auth-js` 2.116.0.

**With a caveat that is not settled for this project.** `getClaims` is local and fast only with an
**asymmetric** signing key (RSA/ECC), verifying against the published JWKS. Supabase's older model
is a single shared HS256 secret, still supported for backward compatibility and **still what a
project gets unless it has moved**. This repository's `config.toml` has `signing_keys_path`
commented out. So "our auth check is local" is currently an assumption, not a measurement — see
_Contested_ below.

### 3 · `setAll` takes a second argument, and dropping it can serve one user's session to another

This is the serious one. From the installed `@supabase/ssr` 0.12.6 type definitions:

> _"Headers that must be set on the HTTP response alongside the cookies. Responses that set auth
> cookies must not be cached by CDNs or reverse proxies, **otherwise one user's session token can be
> served to a different user**."_

The library passes `Cache-Control: private, no-cache, no-store, must-revalidate, max-age=0`,
`Expires: 0` and `Pragma: no-cache`. The same block adds a second constraint:

> _"For a server client, the cache headers are delivered only with the first cookie write. **A new
> server client must be created for each request**; reusing one across requests would leave later
> responses without the required cache headers."_

**Measured here:** `src/lib/supabase/server.ts` implements `setAll: (list) => …` — one parameter. The
headers argument is not merely unused, it is not received. Today that is harmless, because nothing
authenticates and no CDN sits in front; it is harmless the way an unlocked door is harmless in an
empty building. It is a cross-**user** leak in the layer whose entire product claim is isolation, and
it would arrive silently the first time a session and a cache exist together.

The same type also carries a timing rule I would not have known to write down: call `getClaims()`
**early in the request handler, before any response is generated**, or a refresh that completes after
the response is committed is lost, and the next request refreshes again.

### 4 · Server Actions are public POST endpoints, and a page check does not cover them

From the Next.js data-security guide, verbatim:

> _"By default, when a Server Action is created and exported, it is reachable via a direct POST
> request, not just through your application's UI. This means, even if a Server Action or utility
> function is not imported elsewhere in your code, it can still be called externally."_

> _"A page-level authentication check does not extend to the Server Actions defined within it. Always
> re-verify inside the action."_

Next.js encrypts action ids and eliminates unused actions, and says plainly what that is worth:
it _"reduces the risk in cases where an authentication layer is missing. However, you should still
treat Server Actions as reachable via direct POST requests."_ A mitigation, not a boundary.

**And proxy coverage of an action is an accident of where the action lives:**

> _"Server Functions are not separate routes in this chain… a Proxy matcher that excludes a path will
> also skip Server Function calls on that path. A matcher change or a refactor that moves a Server
> Function to a different route can silently remove Proxy coverage."_

ADR-011 makes every mutation a Server Action. So for keelblock this is not an edge case, it is the
mutation path: **authorization in the proxy layer is coverage that a file move can delete.**

### 5 · The email rate limit makes magic-link auth unusable before it makes it insecure

Supabase's production checklist: the default auth email rate limit is **2 emails per hour**, and
_"You can only change this with your own custom SMTP setup."_ A magic-link-first product without
custom SMTP does not degrade — it stops, project-wide, at the third login of the hour.

The same page raises a failure mode I had not accounted for: **enterprise mail scanners fetch links
before the user does**, consuming a single-use magic link and presenting the user with an expired
one. The documented mitigation is a link to a domain you control that redirects on click.

## What this repository inherits rather than states — F-31, in the auth surface

F-31's rule is _if a security property is true because of a default you did not set, it is not a
property, it is a version of somebody else's image._ The `[auth]` block in `supabase/config.toml` is
the CLI's generated file with the generated comments, unedited. Measured today:

| Setting                         | Value here        | What it means                                                   |
| ------------------------------- | ----------------- | --------------------------------------------------------------- |
| `[auth.sessions]`               | **commented out** | no `timebox`, no `inactivity_timeout` — a session never expires |
| `minimum_password_length`       | `6`               | the file's own comment says "recommended 8 or more"             |
| `password_requirements`         | `""`              | none                                                            |
| `enable_confirmations`          | `false`           | email ownership is never proven                                 |
| `[auth.mfa.totp]`               | `false` / `false` | off (and Pro-plan gated)                                        |
| `[auth.captcha]`                | commented out     | no bot check on the auth endpoints                              |
| `enable_refresh_token_rotation` | `true`            | **good — and unstated**, which is the point                     |

The last row is the one that makes the argument. Rotation is on because Supabase chose well, not
because keelblock chose. It is correct today by the same mechanism that made `anon`'s table grant
correct on one Postgres image and wrong on the next.

**And none of it governs production.** There is no `[remotes]` block, so this file configures the
local stack and nothing else; a deployed project's auth settings would live in a dashboard, outside
the repository, unreviewed and undiffable. Supabase supports config-as-code for exactly this — a
`[remotes]` block keyed by project id, applied on push — which turns every row above from an
inherited default into a reviewed line in a diff.

## Settled / contested

**Settled**, and safe to specify against: the `getSession`/`getUser`/`getClaims` split · the
`setAll` cache-header contract and the per-request client rule · Server Actions as public POST
endpoints requiring their own authorization · the `proxy` rename · PKCE (`exchangeCodeForSession`)
for the OAuth and magic-link callback · the redirect allowlist, with Supabase recommending exact
paths in production and treating globstar as a development convenience · the 2/hour email limit.

**Contested or unmeasured**, and to be labeled as such in the spec rather than asserted:

- **Whether `getClaims()` verifies locally on this stack.** It depends on the signing key type, and
  this project has not chosen one. Measure before SPEC-004 is `done`; the answer changes whether
  every authorized request makes a network call to the Auth server.
- **`encode: "tokens-only"`** is marked `@experimental` in the library types. Attractive — it keeps
  the user object out of the cookie — and not something to build a spec on yet.
- **Passkeys.** The CLI config has commented `[auth.passkey]` and `[auth.webauthn]` blocks. That is
  evidence the CLI knows about them; it is not evidence about maturity, and I did not verify it.
- **Per-account lockout.** Already filed as DEF-006 with the right reasoning: Supabase's limits are
  per-IP, and rotating IPs defeats them. Nothing found here changes that.

**Plan-gated, and therefore an honesty constraint rather than a technical one:** MFA and leaked-
password protection (HaveIBeenPwned) are Pro-plan features. keelblock can ship the configuration and
the tests; it cannot promise a free-tier buyer the behavior.

## What keelblock should do

1. **State the auth configuration in the repository**, including the values that are correct by
   default today, and add a `[remotes]` block so production is governed by the same file.
2. **Authorize in the Data Access Layer**, not in the proxy. The proxy refreshes the session; the
   thing that touches data decides. This is also Next.js's own recommendation.
3. **Every Server Action re-verifies**, and that is a testable property rather than a review habit.
4. **Take the `setAll` headers argument**, create the server client per request, and assert both —
   this is the one finding here that is a cross-user leak rather than a hardening item.
5. **Verify with `getClaims()`**, and measure whether it is local on this stack before claiming it.
6. **Rename `middleware.ts` to `proxy.ts`** with the codemod, so the file matches the framework the
   rest of the spec is written against.

## The version note this memo will go stale on

Verified against Next.js `16.3.4` (docs dated 2026-09-07), `@supabase/ssr` `0.12.6`,
`@supabase/supabase-js` and `@supabase/auth-js` `2.116.0`, as installed. Both the `proxy` rename and
the `getClaims` recommendation are recent enough that a reader six months from now should assume the
advice moved again, and re-read before trusting this. That is what `moderate` volatility means in
`manifest.json`, and why the date on this memo is a claim rather than a formality.
