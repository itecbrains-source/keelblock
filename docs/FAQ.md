# Questions

Answered from evidence in this repository. **Every answer cites something you can open and check** —
if an answer here ever rests on an assertion instead, that is a defect.

---

### Is my tenants' data actually isolated, or do you just say so?

Open [`docs/ACCESS-MATRIX.md`](ACCESS-MATRIX.md). It is generated by probing the live database as
each identity — unauthenticated, a member, **a real user of a different organisation**, the service
role — and recording what each could actually do to every table. It is regenerated on every run, and
a stale copy fails the build.

The row that matters is "Authenticated · different organisation". A new tick in it is a tenant leak,
caught in a document during review rather than by a customer.

### How is that different from what every other kit claims?

They enforce isolation in application code. The most popular free kit does this ([F-15](FINDINGS.md)):

```ts
const row = await getById(id); // any tenant's row, by id alone
if (row.teamId !== teamId) throw new ApiError(403); // and now it is in memory
```

Read the order. The other tenant's row is in the process — and in the query log — **before** anything
decides you were not allowed to see it. Under row-level security it is never selected; the predicate
is inside the query plan, and there is no second step to forget.

We checked rather than assumed: a search for `create policy` across that project's schema and library
returns zero matches, and there is no ORM middleware applying scope centrally either. Roughly fifty
query sites each carry the obligation individually.

### Why should I believe your tests actually test anything?

Because we published the case where ours did not. [F-13](FINDINGS.md): keel's own unit gate ran
`vitest --passWithNoTests` against **zero test files** and printed a green tick, while the function
generating the access matrix had no test at all — the rule requiring a proof-of-failure was violated
by the gate enforcing it.

Every gate now ships a **mutation proof**: a test that restores the real defect and asserts the gate
goes red. A green run is evidence rather than agreement.

### Have you found anything real, or is this theoretical?

Twenty-two findings with reproductions in [`docs/FINDINGS.md`](FINDINGS.md). The one with the widest
reach: on a default Supabase project, an unauthenticated `anon` role could **`TRUNCATE` every tenant
table** ([F-1](FINDINGS.md)). RLS does not apply to `TRUNCATE`, so no policy and no policy test could
see it. It affects every project inheriting the same defaults.

**Three of the twenty-two are our own mistakes.** They are published for the same reason as the rest.

### Why is the Content-Security-Policy report-only? That sounds weak.

It is measured, not timid ([F-16](FINDINGS.md)). A production Next build serves **13 inline scripts**,
so an enforcing `script-src 'self'` blocks hydration and the page never loads. You can have any two
of {strict CSP, static prerendering, working hydration} — a per-request nonce is genuinely strict and
costs prerendering outright, because prerendered HTML was fixed at build time and carries no matching
attribute.

So the six non-CSP headers are **enforced unconditionally** and the CSP reports. `KEEL_SECURITY_HEADERS=on`
enforces it once you have tuned it for your own application. Shipping `'unsafe-inline'` and calling
that protection was the alternative.

### Will this still be current in a year?

That is the question this project takes most seriously, because the free alternatives are three
framework majors behind while remaining actively maintained.

A **freshness gate** fails the build when a dependency is more than one major behind, or when a
verification stamp expires. On its first run it found keel **already two majors behind** — `create-next-app`
pins TypeScript 5 while 7 is current ([F-18](FINDINGS.md)). A weekly clean-clone build installs from
scratch and runs everything, because a template has no users to exercise it.

### Why only Next.js?

So that feature-completeness is affordable. The paid kits maintain the same feature set across three
frameworks; keel maintains one, which is roughly three times the budget per feature.
[ADR-012](adr/ADR-012-framework-portability.md) records what keeps a future port cheap — the schema,
policies, proof harness, gates and access matrix are already framework-agnostic, so a port rewrites
the view layer and inherits the guarantee.

### Can I remove the parts I do not want?

That is a tested property rather than a promise — bar **B-6** in [`docs/PRODUCT.md`](PRODUCT.md): deleting any optional subsystem leaves
typecheck, build and the remaining suite green. It exists because the loudest complaint about starter
kits is that retrofitting one to your needs costs more than writing the feature yourself.

### What is free and what do you charge for?

Everything in this repository is MIT and always will be. The paid tier is **audit evidence** — SOC 2
export, auditor pack, traceability ([ADR-009](adr/ADR-009-open-core-boundary.md)).

The line is: developers do not pay for tests, companies pay for what they hand an assessor. And it is
mechanised, not promised — **keel's full claim must hold with zero paid components installed**, and a
gate asserts it.

### I cloned it six months ago and you fixed a security bug. How do I get it?

The question every starter fails ([ADR-008](adr/ADR-008-upgradability.md)). The answer rests on where
security fixes actually land: **policies are migrations, and a new migration file cannot conflict**
however far your project has diverged. So the most important class of fix is deliverable by
construction, with codemods for mechanical changes and a CI job that proves the path from the
previous tag.

### Is it production ready?

Not yet, and the README says so. The tenancy layer, proof harness and gates are built and green; auth,
billing and the product surfaces are specified and not built — see [`spec/README.md`](../spec/README.md).

If that distinction ever blurs, the project has failed its own first rule.
