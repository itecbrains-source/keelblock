# Getting started

From nothing to a running application with a green proof suite. **Every shell block on this page is
executed on a clean runner on every push** (SPEC-012) — if a command here is wrong, the build fails,
which is why you should trust it more than you would normally trust a setup page.

What it cannot tell you is whether the page is any good. A machine will happily execute an
incomprehensible sequence. Whether a newcomer can follow it is measured separately, by the handover
trial (B-11), and its human half is deliberately still open.

## Before you start

Node 26 · Docker, for the local Supabase stack · the
[Supabase CLI](https://supabase.com/docs/guides/cli) · `psql`, because the gates query the database
directly · Python 3.10+, for the policy prober.

You do not need to check these by hand. `npm run check` names any that is missing, with how to
install it, rather than failing with a stack trace.

## Create the project

```bash
npx create-keelblock-app my-app
cd my-app
```

That gives you a project with its own git history and one commit — not a clone of keelblock's. It also
records where it came from, in `keelblock.provenance.json`, which is what lets it take a later
release. See [Upgrading](#upgrading).

## Install

Two installs, because the proof suite is not all JavaScript. The policy prober is a Python tool, and
it is the thing that probes every table, command and identity.

```bash
npm install
python3 -m venv .venv && ./.venv/bin/pip install -r requirements.txt
```

## Start the database

```bash
supabase start
```

The first run pulls container images and takes a few minutes. Afterwards it is seconds.

## Prove it

```bash
npm run check
```

This is the whole loop: types, a production build, format, lint, unit tests, translations, dead code,
staleness, the promises the documentation makes, the boundary that stops application code reaching
around row-level security, the schema guard, **the policy suite that probes every table × command ×
identity**, and every committed generated artifact.

It reports every failure rather than stopping at the first, because a checker that stops at the first
makes you run it six times.

## Run the application

```bash
cp .env.example .env.local
```

Fill it from `supabase status`, then:

```bash ignore starts a long-running server, which a walkthrough runner cannot exit
npm run dev
```

Sign in is a magic link. There is no password — that is a decision, and
[ADR-021](adr/ADR-021-password-sign-in.md) records it along with what it costs. In local development
the mail lands in the Supabase Inbucket at the URL `supabase status` prints.

## Upgrading

Your project is a copy, so the interesting question is what it remembers. It remembers the release
and the commit it came from, and it keeps a remote pointing home — unfetched, because fetching
keelblock's history at creation time would have cost you minutes you may never need.

So an upgrade is two commands rather than one:

```bash ignore there is no newer release to take during a walkthrough of the current one
git fetch upstream --tags
node scripts/upgrade.mjs <newer-ref>
```

It takes the files upstream owns — migrations, intent tests, scripts, specs, ADRs — leaves everything
else alone, and says out loud which files it left and which you must regenerate. That path is
executed on every push, against a project generated by the same command you ran above.
